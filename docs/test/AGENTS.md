# Test Documentation Instructions

## Directory contract

- `docs/test/**/*.md` は `README.md` と `AGENTS.md` を除き、すべてテスト仕様書とする。
- `README.md` および `AGENTS.md` はテスト仕様書として扱わない。
- この配下の `AGENTS.md` はテスト文書にだけ適用し、アプリケーションコードやテスト実装のルールにはしない。

## README.md の記述規約

- `README.md` には各仕様書に定義されたテストケースの一覧テーブル（索引）を記述する。
- テストケースの一覧テーブルにはカテゴリとは別に `区分` 列を設け、本文の区分と一致させる。仕様書内の一覧テーブルも同様とする。
- テスト実行方法、検証境界、記述規約などの運用指示および技術仕様は、各ディレクトリの `AGENTS.md` を正とする。

## テスト仕様書の共通規約

- 観測可能な振る舞いを日本語で記述し、目的、明示的な ID の anchor と見出し、カテゴリ、区分、Given / When / Then を持たせる。ID・カテゴリ・fixture などの詳細は各階層の `AGENTS.md` に従う。
- 仕様とテスト実装の対応には Test ID を使う。仕様書や索引に `対応テスト`、`対応ファイル`、`対応 Story`、予定テスト名、実装対応列、テストファイルへのリンク、コピーしたテスト名、Story export 一覧を記述しない。
- ケースの契約に実装場所を含めない。共通の実行方法として runner 設定やテストディレクトリを説明することは許可するが、ケース単位の実装対応表にはしない。
- Given には必要な状態を記述し、Given / When / Then はそれぞれ1ブロックを原則とする。独立した振る舞いは別ケースに分け、parameterized input や表示 variant は実装名ではなく状態と期待結果として記述する。
- 対応欄を削除するときに ID、anchor、カテゴリ、前提、期待結果、関連仕様リンクを変更しない。対応欄の削除だけを理由にケースを改番しない。
- 共通の文書ルールはこのファイル、階層固有の文書ルールは子の `AGENTS.md` に置き、repository root の `AGENTS.md` へ重複して記述しない。
- Firestore / Storybook 契約以外の runtime behavior 仕様は `e2e` に置く。明示的な依頼なしに別の unit / integration 仕様書や ID system を追加しない。
- ID が存在するだけではテスト済み・検証済みとはみなさない。未実装、skip、TODO は明示し、合格した検証として扱わない。
- 対応テストの参照チェックを保留するケースは、見出しの ID 直後にだけ `[TODO]` を付ける。例: `### STORYBOOK-ACCOUNT-06 [TODO] 認証状態と UID を表示する`。対応するテストを実装したら印を削除する。状態行や `done` は記述せず、索引にも印を重複させない。印がないことはチェック対象を意味し、検証済みを意味しない。

## テスト仕様書テンプレート

新規仕様書は次のテンプレートを使い、`{...}` を対象の振る舞いに置き換える。
ID・カテゴリは各階層の規約に従い、anchor は ID を小文字にした値とする。区分はケースに応じて正常系・異常系を選ぶ。
ケースを追加するときは一覧の行と anchor 以降を繰り返し、`README.md` の索引も更新する。

テスト仕様書の構成は、文書タイトル、`目的`、`テストケース`、各ケースの見出しと `カテゴリ`・`区分`・`Given` / `When` / `Then` に限定する。
このテンプレートにないセクション・サブセクション（`共通前提`、`補足`、`実装方針` など）の作成を禁止する。階層固有の必須情報や関連仕様へのリンクは既存の項目内に記述し、共通の実行・検証前提は各階層の `AGENTS.md` に置く。

```markdown
# {対象} テスト仕様書

## 目的

{このテスト層で確認する振る舞いを簡潔に記述する。}

## テストケース

| ID | カテゴリ | 区分 | テストケース |
| --- | --- | --- | --- |
| {TEST-ID} | {カテゴリ} | 正常系 | [{確認する振る舞い}](#{test-id}) |

<a id="{test-id}"></a>

### {TEST-ID} {確認する振る舞い}

カテゴリ: `{カテゴリ}`

区分: 正常系

Given:

- {操作前の状態・入力・権限など、再現に必要な前提}

When:

- {このテスト層の公開された境界を通した操作、または外部から起きる事象}

Then:

- {その境界で観測できる結果を、値・表示・保存内容などで具体的に記述する。}
```

E2E では Given の先頭に `Fixture: [名前](./fixture/名前.yaml)` を追加するなど、階層固有の必須項目を補う。
共通の実行・検証前提は各階層の `AGENTS.md` に置き、ケース本文には実装手順ではなくケース固有の状態と期待結果を書く。
未実装で参照チェックを保留する場合は、共通規約に従い見出しだけを `### {TEST-ID} [TODO] {確認する振る舞い}` とする。

## 正常系・異常系の区分

- 各ケースのカテゴリの直後に、独立した段落で `区分: 正常系` または `区分: 異常系` を記述する。カテゴリは操作や検証対象の分類、区分はシナリオの正常・異常の分類であり、互いに置き換えない。
- 既存の一つの ID に正常・異常の独立した入力例や操作が含まれる場合は、`区分: 正常系 / 異常系` と両方を併記する。区分の追加のためにケースを分割・改番せず、新規ケースでは従来どおり独立した振る舞いを分ける。
- `正常系`: その観測境界で有効な入力と利用可能な状態で、仕様で認められた操作・表示・状態遷移を確認する。0件表示、任意項目の未入力、利用者によるキャンセル、許容範囲内の境界値、対応するオフライン利用も含む。
- `異常系`: 不正な入力、権限不足、必要なデータの欠落・破損、通信・保存・初期化の失敗に対する拒否、エラー表示、安全な無変更や復旧を確認する。
- Given / When で設定したシナリオに基づいて分類し、Then に付記した別条件だけで両方の区分にしない。「表示されない」「変更しない」などの否定表現や境界値だけを理由に異常系としない。失敗からの復旧は、最終的に成功しても異常系とする。
- 区分はテストの合否や実装状況を表さない。異常系でも、期待した拒否や復旧を確認できればテストは成功である。
- 区分の追加だけを理由に、既存の ID・anchor・カテゴリ・Given / When / Then を変更しない。
