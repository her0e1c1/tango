# Store 単体テスト仕様書の記述規約

## 検証境界

- 利用側から観測できる Entity の状態遷移、参照結果、設定の保存・復元を扱う。内部のオブジェクト形状、配列の参照同一性、Zustand の通知回数、フックの再レンダリング回数、JSON の構造だけを目的としたケースは作らない。
- Given は業務上の状態・入力、When は公開境界への操作またはイベント、Then は利用側が取得できる結果と維持される条件として書く。関数名、実装ファイル、テストの準備手順を振る舞いの代わりにしない。
- ケース本文は「何をしたとき、どの内容を参照できるか」で記述する。SDK・Promise・callback の制御順、保存フィールドの構造、関数の分割をケースの契約にせず、mock の方法は共通の検証前提に置く。
- 異なる公開操作・異なる期待結果は1つのケースにまとめず、独立したテストケース ID に分割する。作成・編集・削除や開始・進行・終了を1ケースの表にまとめない。同一の振る舞いに対する正常値・空・境界値・互換データなどの入力パターンだけをパラメーター化する。

| 対象 | 操作・観測する契約 |
| --- | --- |
| Auth | 認証状態の変更と、現在の認証状態・本人情報の参照 |
| Card | 取得結果の置換・クリア、保存した変更を取得するまでの状態、および所属デック・所有者に応じたカードの参照 |
| Deck | 取得結果の置換・クリア、保存した変更を取得するまでの状態、および現在のデック一覧の参照 |
| Preference | 設定の部分変更・切り替えと、保存設定から復元した値の参照 |
| Study Session | クリア、所有者・取得結果・取得終了の通知、保存した変更を取得するまでの状態、および再開対象・取得待ちの参照 |

## 共通の検証前提

- 初期状態は期待値を事前に書き込んで確認しない。復元は変更後のメモリ状態を引き継がず、保存データだけから確認する。
- 更新・削除では、影響を受けてはいけないデータも非既定の値で用意する。対象外の値が既定値に戻る誤りと、正しく維持される結果を区別できること。
- 外部境界だけをテスト側で置き換え、検証する操作・参照・保存復元ロジックは実物を使う。Card の参照可能デックと設定の保存先は外部境界として用意してよい。
- Firestore を使うケースでは SDK と Firebase 初期化だけをテスト側で mock し、Entity の公開操作・購読処理・データ変換・状態更新・参照処理は実物を使う。認証済みの本人情報と、Card の参照可能デックは公開操作を通して用意する。この購読境界の検証では、Entity や公開 query を mock せず、状態置換操作を直接呼んで取得結果の通知を代用しない。
- 購読ケースの Given / When / Then には、購読開始、外部データソースからの取得結果またはエラー通知、公開 query で観測できる結果を明記する。購読通知を受けるまでは取得済み状態を維持し、通知後の置換と購読エラー時の維持を中心に検証する。
- SDK の snapshot・エラー通知と書き込み応答をテスト側で制御し、mock が自動で store を更新しないようにする。mock に Rules・キャッシュ・同期・rollback の実装を持たせない。保存 workflow の成否はここで検証しない。
- 保存した変更を取得するまでの状態を確認するケースは、snapshot 受信前後の公開 query の値を比較する。同じ操作を既存の Firestore 結合テストが扱っていても、この通知前の無変更の契約は区別する。
- 設定の互換復元は既存の保存先 `tango-config`、旧学習バックアップの保持は `tango-study` を対象とする。ケース本文では保存先のキーやラッパー構造ではなく、復元・保持される内容を記述する。

## 他のテストとの役割分担

- Firebase Auth の認証処理、過去の認証試行や購読からの遅延通知、認証変更時の各 Entity の消去はアプリケーションの結合テストで扱う。クリア操作単独の確認を、サインアウト全体の検証と表現しない。
- Firestore の document 検証、論理削除の保存、実際の購読・通信エラー、Rules の認可、リモート保存は [Firestore 結合テスト仕様書](../../integration/firestore/) で扱う。ここでは通知を受けたアプリケーションの状態遷移だけを確認し、SDK を mock した購読テストを実通信・保存・rollback の検証済み証拠にはしない。
- 画面の表示と操作は [Storybook 結合テスト仕様書](../../integration/storybook/)、ユーザーの一連の操作は [E2E テスト仕様書](../../e2e/) で扱う。同じ保証を既存の結合テストが十分に検証している場合は、同じ内容の単体テストを増やさない。
- カード選定、FSRS、保存失敗からの再試行など、別の規則・ワークフローはここへ追加しない。

## ケースの書式と対応

- [共通規約とテンプレート](../../AGENTS.md) に従う。ID は既存の `UNIT-STORE-<AUTH|CARD|DECK|PREF|STUDY>-<NN>` を使い、索引、アンカー、見出しをそろえる。README.md は全ケースの索引だけを記載する。
- 仕様とテストの対応は ID だけで表し、既存テスト名・実装ファイルへのリンク・対応状況の表や状態行を記述しない。
- 未実装・要補完のケースは見出しの ID 直後の `[TODO]` で示す。部分的なアサーションや ID の一致だけで、Given の全入力と Then の全結果が検証されたとは扱わない。
- 仕様書の変更だけを理由に、本番実装を期待値の根拠にしたり、テストを実行済みと記述したりしない。
