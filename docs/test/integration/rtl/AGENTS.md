# React Testing Library 結合テスト仕様書の記述規約

## 検証境界

- 画面・router・状態管理・model/action を組み合わせた、操作後の状態や遷移などロジック寄りの振る舞いを対象とする。見た目、レイアウト、表示 variant の詳細は Storybook、実際の保存・購読・Rules は Firestore、代表的な利用導線は E2E で確認する。
- 実際の画面操作と公開 API で状態を準備し、画面や router の遷移先、公開された状態から結果を確認する。検証対象の画面・router・状態の連携を mock しない。認証・通信・保存など対象外の境界はテスト側で置き換えてよい。
- Memory router の直接入場や再マウントは、読み込み済みの状態とアプリの経路解決の契約である。ブラウザー再読み込み、サーバーの routing、Firestore の永続化・復元を保証しない。
- 詳細なロジック、境界値、取り違えなどの回帰は、観測可能な振る舞いとしてここへ記述する。実装の分岐・private 関数・mock の呼び出し回数だけから期待結果を作らない。

## 書式と ID

- [共通規約](../../AGENTS.md) のテンプレートを使用する。README はケースの索引とし、実装対応表を書かない。
- ID は `RTL-<大文字の仕様ファイル名>-<NN>` とし、カテゴリは状態・遷移を読む `read` または操作で状態を変える `write` とする。正常系・異常系の区分を別に記述する。
- Given には入力・認証・読み込み済みの状態・対象外の境界の条件を、When には操作や外部事象を、Then には操作後の観測可能な結果を書く。parameterized case は代表値と境界値、それぞれの期待結果を明記する。
- 各 `it` / `it.each` のタイトルを仕様 ID で始める。同じ契約の parameterized rows は ID を共有できる。移動時は関連する unit / integration test の参照も更新する。
- 未実装や一部未検証のケースは見出しの ID 直後に `[TODO]` を付ける。ID の記載や lint 合格は実行成功の証拠ではない。

## 実行と確認

- RTL 結合テストは `test/integration/**/*.spec.{ts,tsx}` に置き、既存の Vitest `integration` project で実行する。Firestore 用の emulator が不要な RTL テストは対象ファイルを指定して実行できる。
- `npm run lint:test-specs` と `npm run lint:markdown` で参照と形式を確認する。参照 lint は文字列照合であり、実行条件やアサーションの網羅性はレビューと実行で確認する。
- E2E から詳細な契約を移すときは、E2E に残す代表導線と RTL で保証する範囲を区別し、仕様・参照・実装を同時に更新する。他のケースは個別に検討し、一括で削除しない。
